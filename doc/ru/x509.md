# Коллектор сертификатов X509
X509 — список конфигураций для проверки сертификатов в файловой системе. Эту опцию можно использовать несколько раз в файле конфигурации.\
Она запускает рекурсивный обход каталогов для поиска всех файлов, в имени которых есть указанная в опции `match` часть, и пытается их разобрать.

## Обзор
```
x509
{
    name first_context;
    path /etc/ssl;
    match .crt;
    period 60s;
}
x509
{
    name second_context;
    path /etc/nginx;
    match .pem;
}
x509
{
    name third_context;
    path /etc/kafka;
    match .jks;
    type jks;
    password jkspass;
}
```

## name
Задаёт только имя контекста.\
На сбор метрик это не влияет; это исключительно ключ для обновления полей контекста x509 через API Alligator.

## path
Задаёт начальный путь для рекурсивного разбора и обхода каталогов в поисках сертификатов.

## match
Задаёт часть имени файла, по которой файл считается сертификатом и разбирается.

## period
Задаёт период повторного разбора сертификатов в контексте. Значение по умолчанию — `10s`.

Подробнее о единицах, которые можно указывать в конфигурации, см. в [документации по конфигурации](../configuration.md).

## type
Возможные значения:
- pem
- jks
- pfx

Эта опция задаёт метод разбора файлов сертификатов для данного контекста. Значение по умолчанию — `pem`.

## password
Задаёт пароли для открытия архивов PFX/JKS.

## ca_file
Необязательный путь к PEM-пакету CA (или одному CA), используемому для проверки цепочки сертификата при проверке PEM/PFX в файловой системе.
Без `ca_file` сбор с диска проверяет только срок действия (`notBefore`/`notAfter`).
Сопоставление hostname/CN/SAN для проверок файловой системы не выполняется (только для сетевых TLS-проб).

## crl_file
Необязательный PEM (или DER) CRL для пометки сертификатов в файловой системе как отозванных (`x509_cert_valid{reason="revoked"}`).

## crl_scope
`leaf` (по умолчанию) проверяет только конечный сертификат. `chain` также требует CRL для промежуточных (`X509_V_FLAG_CRL_CHECK_ALL`).

## ocsp
`on` включает OCSP-запрос по URL AIA из сертификата или по `ocsp_responder`, если он задан. При проверках файловой системы ответ всегда запрашивается inline.

## ocsp_responder
Переопределяет OCSP URL из AIA сертификата (`http://` или `https://`).

## ocsp_proxy
HTTP- или SOCKS5-прокси только для OCSP-запроса (`http://`, `socks5://`, `socks5h://`). Не зависит от `proxy=` у scrape.

## ocsp_timeout
Таймаут HTTP для OCSP. По умолчанию `3s`.

## ocsp_cache_ttl
Верхняя граница кэша результата OCSP. По умолчанию `1h`. Кэш также учитывает `nextUpdate`.

## revocation_mode
`soft` (по умолчанию): ошибки responder/загрузки CRL не проваливают проверку; ответ «отозван» всегда проваливает.
`hard`: unknown/error/no-responder тоже проваливают проверку.

## Примеры использования

### Мониторинг PEM-сертификатов
```
x509
{
    name nginx-certs;
    path /etc/letsencrypt/live;
    match .crt;
}
```

### Мониторинг PEM-сертификатов с проверкой цепочки/CA
```
x509
{
    name nginx-certs;
    path /etc/letsencrypt/live;
    match .crt;
    ca_file /etc/ssl/certs/ca-bundle.crt;
}
```

### Мониторинг PEM-сертификатов с CRL и OCSP
```
x509
{
    name nginx-certs;
    path /etc/letsencrypt/live;
    match .crt;
    ca_file /etc/ssl/certs/ca-bundle.crt;
    crl_file /etc/ssl/ca.crl;
    ocsp on;
    ocsp_responder http://ocsp.example.com/;
    ocsp_proxy http://proxy:3128;
    revocation_mode soft;
}
```

### Мониторинг JKS-сертификатов
```
x509
{
    name kafka-certs;
    path /etc/kafka/;
    match .jks;
    type jks;
    password 123456789;
}
```

### Мониторинг PFX-сертификатов
```
x509 {
    name pfx;
    path /app/src/tests/certs;
    match .pfx;
    password 123456;
    type pfx;
}
```

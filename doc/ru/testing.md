# Модульные тесты и покрытие

Набор `src/tests/unit2/` организован по заголовкам функциональности (например `netlib.h`, `http.h`, `parsers.h`) и держит тесты рядом с production-кодом.

> Сборка тестов требует зависимостей проекта (например `jansson`) и инициализированных submodules.

## Запуск покрытия

Запуск покрытия (область: `src/**/*.c`, без `src/tests/**`, `src/external/**`, `src/build/**`):

```
cd src
./tests/coverage/run_coverage.sh
```

Артефакты:

- `src/tests/coverage/coverage_report.txt` — полный вывод `llvm-cov report`
- `src/tests/coverage/coverage_top15.txt` — 15 файлов с наименьшим покрытием
- [coverage-baseline.md](../coverage-baseline.md) — базовый снимок и пороги

Минимальный порог локально:

```
cd src
MIN_LINE_COVERAGE=50 ./tests/coverage/run_coverage.sh
```

# Принципы модульного тестирования

Этот документ задаёт контракт для модульных тестов в `src/tests/unit2`.

## Область и фреймворк

- Новые unit-тесты добавляются в `src/tests/unit2`.
- Легаси-набор `src/tests/unit` не является целью для новых тестов.
- Тесты группируются по production-подсистемам (events/config/parsers/common).

## Детерминизм и изоляция

- Unit-тесты не должны зависеть от внешних сетевых сервисов.
- Избегайте фиксированных `sleep` в unit-тестах.
- Предпочитайте in-memory фикстуры или локальные статические фикстуры в `src/tests/mock`.
- Если тест пишет файлы, используйте детерминированные временные пути и удаляйте артефакты.
- Каждый тест инициализирует только нужное состояние и освобождает/сбрасывает его по завершении.

## Проверки и поведение

- Проверяйте и успешные, и ошибочные пути.
- Утверждайте семантическое поведение (коды возврата, флаги, выбранные поля), а не только ненулевые указатели.
- Включайте граничные случаи (пустой ввод, некорректный ввод, границы длин).
- Для тестов парсеров проверяйте статус парсера и важные фрагменты выходных данных.

## Политика покрытия

- Покрытие измеряется `llvm-cov` через `src/tests/coverage/run_coverage.sh`.
- Область покрытия — production C-файлы в `src/`, без test/external/build путей.
- CI-гейт покрытия должен требовать минимальный суммарный порог line coverage.

## Ожидания к pull request

- Новый или изменённый production-код должен включать или обновлять unit-тесты в том же изменении.
- Изменения поведения parser/config/events должны включать хотя бы один тест на крайний или ошибочный путь.
